## Abstract

ID-CLOSE VAULT is a client-side zero-knowledge cryptographic storage system designed for journalists, activists, whistleblowers, and privacy defenders operating under hostile inspection regimes. The system implements a **dual-partition plausible deniability protocol** in which a single fixed-size binary container (`.bin`) harbors two cryptographically isolated volumes — a primary (decoy) partition and a secondary (hidden) partition — without any partition table, boundary marker, or structural metadata that would reveal the existence of dual volumes to a forensic examiner.

Every container produced by ID-CLOSE VAULT is a fixed-size block of cryptographically secure pseudo-random noise with Shannon entropy approaching 8.0 bits per byte. The container possesses zero magic bytes, zero identifiable file headers, zero plaintext metadata, and is mathematically indistinguishable from uniform random output generated by the platform CSPRNG. Decryption occurs exclusively client-side inside volatile memory via the Web Crypto API (`SubtleCrypto`), with no server roundtrips, no telemetry, and no persistent storage of vault content.

For Pro-tier containers (>50 MB), the system employs an **HKDF Tier-Binding Trapdoor** that mathematically binds the Ed25519 license signature bytes to the AES-256 encryption key via RFC 5869 HKDF-Expand. Any 1-bit deviation in the signature produces a catastrophically different AES key with overwhelming probability ($2^{-128}$), rendering forged or tampered license tokens cryptographically useless.

The protocol achieves four mutually reinforcing security properties:

1. **Plausible Deniability** — Under coercion, the primary partition is disclosed via the primary passphrase. The secondary partition remains cryptographically inaccessible without the secondary passphrase. An adversary cannot distinguish a single-volume container from a dual-volume container; both partitions reside within the same uniform random distribution.

2. **Post-Mortem Forensic Resistance** — The absence of file headers, magic bytes, or partition tables eliminates signature-based forensic identification. Standard file-carving tools (`photorec`, `scalpel`, `binwalk`) recover nothing from a container because the byte distribution is indistinguishable from CSPRNG output.

3. **Air-Gapped Isolation** — The entire application operates as a Progressive Web App (PWA) with offline-first caching. Once cached, all cryptographic operations execute with zero network packets. The system is designed to be loaded, cached, and then operated on an air-gapped machine with all network adapters disabled.

4. **License-Bound Cryptographic Enforcement** — The HKDF tier-binding trapdoor ensures that Pro-tier encryption keys are mathematically derived from the operator's Ed25519 license signature. Without a valid cryptographic license, the trapdoor context defaults to `INVALID_TAMPERED_TRAPDOOR`, producing a key that cannot decrypt Pro-tier ciphertext.

## 1. Threat Model

ID-CLOSE VAULT defends against four classes of adversary, which may operate simultaneously.

### 1.1 Rubber-Hose Cryptanalysis & Coercion

**Adversary capability:** Physical coercion, legal compulsion, or torture to extract passwords or decryption keys from the operator.

**Defense:** Dual-partition plausible deniability. The operator possesses two independent passphrases:

- The **primary passphrase** decrypts the decoy partition (Volume A), which contains plausible but non-critical content (decoy credentials, non-sensitive documents).
- The **secondary passphrase** decrypts the hidden partition (Volume B), which contains the operator's actual sensitive assets.

The container format provides no structural evidence of dual volumes. Both partitions occupy halves of a uniformly random byte array. Without the secondary passphrase, the hidden partition is computationally infeasible to distinguish from random noise, and the existence of a second volume cannot be proven through cryptanalysis, statistical analysis, or forensic examination. The operator can truthfully disclose the primary passphrase under duress without compromising the hidden partition.

### 1.2 Post-Mortem Forensic Analysis

**Adversary capability:** Physical seizure of storage media; forensic acquisition via cold-boot attacks, page-file analysis, or disk imaging; post-mortem analysis of deleted files and slack space.

**Defense:** The container is a headerless fixed-size binary blob with:

- Zero magic bytes (`0x00` at all signature offsets)
- Zero identifiable file headers (no PDF `%PDF`, no ZIP `PK`, no ELF `\x7fELF`)
- Shannon entropy ≈ 8.0 bits per byte across the entire container
- Byte distribution statistically indistinguishable from CSPRNG output
- Fixed size aligned to MiB boundaries (10 MB, 50 MB, 100 MB presets)

Standard file-carving tools (`photorec`, `scalpel`, `binwalk`, `foremost`) recover no recoverable artifacts because the container does not contain any recognized file format signature. The container is indistinguishable from a random data dump, encrypted volume header, or any other opaque binary blob.

Additionally, all decryption executes exclusively in volatile memory (RAM). Decrypted content is never written to disk. The 5-minute inactivity auto-purge and explicit `LOCK & PURGE` function zeroize all decrypted buffers in memory before any state could be captured by cold-boot or memory forensics.

### 1.3 Remote Exfiltration & Side-Channels

**Adversary capability:** Network interception, DNS analysis, traffic correlation, server-side logging, remote code execution on network infrastructure.

**Defense:** ID-CLOSE VAULT executes entirely client-side with zero server interaction for cryptographic operations:

- **Zero server roundtrips:** All cryptographic operations (key derivation, encryption, decryption) occur in the browser's Web Crypto API. The server (`server.js`) serves only static files and performs zero cryptography.
- **Zero persistent storage of vault content:** No IndexedDB, no SessionStorage, no cookies used for vault data. LocalStorage stores **only** the offline Ed25519 Pro license signature token (never plaintexts, vault keys, or metadata).
- **Air-gapped operation:** The PWA service worker caches all required assets on first load. Subsequent operation requires zero network connectivity. The system is designed to be loaded on a networked machine, cached, and then transferred to an air-gapped machine via USB.
- **Zero telemetry:** No analytics, no error reporting, no phone-home behavior, no beacon requests.

### 1.4 Live System Attacks (DevTools / DOM / Memory)

**Adversary capability:** Live access to the unlocked browser session; DevTools DOM inspection; JavaScript console manipulation; runtime memory dump; browser extension injection.

**Defense:**

- **DevTools DOM patching:** Decrypted content is rendered transiently in the DOM. The `purgeDecryptedState()` function clears all DOM containers and revokes Object URLs on demand or after 5 minutes of inactivity. An adversary inspecting the DOM after purge sees only empty containers.
- **Console manipulation:** All cryptographic state is held in closure-scoped and module-scoped variables (`_pendingVaultBytes`, `_decryptedState`). These are zeroed via `.fill(0)` on every state transition. Console inspection after purge reveals zeroed buffers.
- **Browser extensions:** Documented OPSEC limitation. Clean browser profiles are recommended for high-threat environments.

## 2. Core Cryptographic Specifications

### 2.1 Authenticated Encryption: AES-256-GCM (NIST SP 800-38D)

Each partition is encrypted using AES-256-GCM (Galois/Counter Mode), providing both confidentiality and integrity in a single pass.

**Formal Specification:**

```
 ciphertext || tag = AES-256-GCM-Encrypt(
   key  = tierDerivedKey,  -- 256-bit, via 2.3
   iv   = CSPRNG(96),      -- fresh 96-bit nonce
   plaintext = padded_payload,
   aad  = absent           -- no additional auth data
 )
```

**Parameters:**

| Parameter | Value | Standard |
|---|---|---|
| Cipher | AES-256-GCM | NIST SP 800-38D |
| Key length | 256 bits (32 bytes) | FIPS 197 |
| Nonce (IV) | 96 bits (12 bytes) | NIST SP 800-38D |
| Auth tag | 128 bits (16 bytes) | NIST SP 800-38D |
| Tag forgery prob. | $2^{-128}$ | GCM security proof |
| IV generation | CSPRNG(96) | Platform CSPRNG |
| Chunked CSPRNG | 64 KiB chunks | Legacy mitigation |

**Nonce Reuse Mitigation:** Each encryption operation generates a fresh 12-byte IV via the platform CSPRNG (`crypto.getRandomValues()`). The IV is never reused across encryptions, containers, or sectors. The chunked CSPRNG function `getSafeRandomValues()` processes buffers in 65,536-byte segments to prevent overflow in legacy browser runtimes.

**Implementation Reference:** `vault.js:160-162` — `crypto.subtle.encrypt({ name: "AES-GCM", iv }, key, plaintext)`

### 2.2 Key Derivation Stage 1: PBKDF2-SHA-256

The initial key derivation converts a user-supplied passphrase into a 256-bit base key using PBKDF2 with SHA-256.

**Formal Specification:**

```
 baseKey = PBKDF2-SHA256(
   password   = passphrase,   -- UTF-8 encoded input
   salt       = CSPRNG(256),  -- 32 bytes, unique per
   iterations = 100,000,      -- work factor
   keyLength  = 256 bits      -- output length
 )
```

**Parameters:**

| Parameter | Value | Standard |
|---|---|---|
| Hash function | SHA-256 | NIST FIPS 180-4 |
| Iteration count | 100,000 | NIST SP 800-132 |
| Salt length | 32 bytes (256 bits) | NIST SP 800-132 |
| Output key length | 256 bits (32 bytes) | AES-256 req. |
| Salt generation | CSPRNG(256) | Platform CSPRNG |

**Security Properties:**

- Each container uses a unique random salt, preventing precomputation attacks (rainbow tables) across containers.
- The iteration count of 100,000 provides substantial resistance against GPU-accelerated dictionary and brute-force attacks.
- The PBKDF2 output is stored transiently in a `Uint8Array` and explicitly zeroed via `.fill(0)` after HKDF expansion (Stage 2).

**Implementation Reference:** `vault.js:72-92` — `crypto.subtle.importKey("raw", ..., "PBKDF2")` → `crypto.subtle.deriveBits(...)`

### 2.3 Key Derivation Stage 2: RFC 5869 HKDF Tier-Binding Trapdoor

The HKDF tier-binding trapdoor is the critical architectural innovation that binds the Ed25519 license signature to the AES-256 encryption key, creating a cryptographically enforced license dependency for Pro-tier containers.

**Formal Pipeline Diagram:**

```
+------------------------------------------------------+
| KEY DERIVATION PIPELINE (Vault Construction)         |
+------------------------------------------------------+
                           |
                           v
+------------------------------------------------------+
| INPUT: Passphrase + CSPRNG Salt (32 bytes)           |
+------------------------------------------------------+
                           |
                           v
+------------------------------------------------------+
| STAGE 1: PBKDF2 (SHA-256, 100,000 iterations)        |
| Output: baseKey (256-bit)                            |
+------------------------------------------------------+
                           |
                           v
+------------------------------------------------------+
| CONTEXT DERIVATION: getTierInfoContext(size)         |
|   <= 50MB:          VAULT_TIER_FREE_STD              |
|   > 50MB+valid sig: VAULT_PRO_ED25519_BOUND          |
|   > 50MB+no sig:    INVALID_TAMPERED_TRAP            |
+------------------------------------------------------+
                           |
                           v
+------------------------------------------------------+
| STAGE 2: HKDF-SHA256 (RFC 5869)                      |
|   IKM  = baseKey                                     |
|   salt = CSPRNG salt (same as Stage 1)               |
|   info = tierInfoContext (per 2.3.1)                 |
|                                                      |
|   Key  = HKDF-Expand(SHA-256, IKM, salt, info, 256b) |
+------------------------------------------------------+
```

#### 2.3.1 Tier Info Context Construction

The `info` parameter to HKDF-Expand is the mechanism that binds the license signature to the derived key:

```
function getTierInfoContext(containerSizeBytes) {
  if (containerSizeBytes <= 50 MB) {
    return encode("VAULT_TIER_FREE_STANDARD");
  }

  // Pro tier: load Ed25519 license token
  signatureB64 = localStorage
    .getItem("vault_pro_token");

  if (!signatureB64) {
    return encode("INVALID_TAMPERED_TRAPDOOR");
  }

  sigBytes = base64urlDecode(signatureB64);
  return encode("VAULT_PRO_ED25519_BOUND:")
       || sigBytes;
}
```

**Three possible `info` contexts:**

| Condition | `info` Value | Result |
|---|---|---|
| ≤ 50 MB | `VAULT_TIER_FREE_STD` | Std AES key |
| >50 MB + valid sig | `VAULT_PRO_` + sig | License key |
| > 50 MB + no sig | `INVALID_TAMPERED` | Trapdoor key |

#### 2.3.2 Proof of Catastrophic Key Divergence

**Theorem:** Let $K_1 = \text{HKDF-SHA256}(\text{IKM}, \text{salt}, \text{info}_1)$ and $K_2 = \text{HKDF-SHA256}(\text{IKM}, \text{salt}, \text{info}_2)$ where $\text{info}_1 \neq \text{info}_2$. Then $\Pr[K_1 = K_2] \leq 2^{-128}$.

**Proof sketch:** HKDF-Expand is built on HMAC-SHA256, which is a pseudorandom function (PRF). For any distinct `info` values, the HMAC inputs differ, and by the PRF security of HMAC-SHA256, the outputs are computationally indistinguishable from independent uniform random strings. The probability of collision between two 256-bit outputs of an ideal PRF is $2^{-256}$, and even a 1-bit difference in `info` produces a completely different PRF evaluation, yielding a different 256-bit AES key with overwhelming probability.

**Practical consequence:** If an attacker forges a license token (modifying the Ed25519 signature by even 1 bit), the `info` context fed to HKDF-Expand changes, producing a completely different AES-256 key. The resulting decryption attempt triggers an AES-GCM authentication tag mismatch ($2^{-128}$ forgery probability), returning `OperationError`. The attacker recovers **zero bytes** of plaintext.

**Test verification:** `test-trapdoor.js:2` (tampered signature rejection) and `test-trapdoor.js:4` (forged signature crack simulation) both confirm this property empirically.

**Implementation Reference:** `vault.js:100-153` — `getTierInfoContext()` + `deriveKeyHKDF()`

### 2.4 Ed25519 License Verification (RFC 8032)

The Ed25519 digital signature scheme is used to verify the authenticity and integrity of Pro-tier license tokens.

**Native Execution Guarantee:**

| Layer | Implementation | Deps. |
|---|---|---|
| Browser (FE) | `importKey("spki", ..., Ed25519)` | Zero |
| Browser (FE) | `verify(Ed25519, ...)` | Zero |
| Node.js | `crypto.sign(null, payload, key)` | Zero |
| Node.js | `generateKeyPairSync("ed25519")` | Zero |

- **Zero polyfills:** No JavaScript Ed25519 implementation is used. All operations delegate to the native browser/OS cryptographic subsystem.
- **Zero npm crypto dependencies:** The `package.json` contains a single dependency (`express`) for the static file server. No cryptographic npm packages are installed.
- **SPKI key format:** Public keys are imported as SubjectPublicKeyInfo (SPKI) DER-encoded structures, the standard format for Web Crypto API key import.
- **64-byte signatures:** Ed25519 produces 64-byte deterministic signatures. The signature is base64url-encoded and stored in the license token wrapper.

**License Token Structure:**

```
Token = base64url(JSON({
  p: base64url(payload),   // { sub, tier, iat }
  s: base64url(signature)  // 64-byte Ed25519 sig
}))
```

### 4.1 Zero-Byte Header Design

Every container produced by ID-CLOSE VAULT satisfies the following invariants:

| Property | Guarantee |
|---|---|
| Magic bytes | None — 0x00 at all signature offsets |
| File headers | None — no PDF, ZIP, or ELF signatures |
| Partition markers | None — no flags, tables, or headers |
| Size headers | None — payload sizes not encoded |
| Timestamps | None — no creation/modification times |
| Metadata | None — no filenames or attributes |
| Shannon entropy | ≈ 8.0 bits/byte (indist. from CSPRNG) |
| Byte distribution | Uniform random; indistinguishable |

### 4.2 Container Topology

```
+-----------------------------------------------------+
|        CONTAINER (fixed, MiB-aligned)               |
|        Uniform CSPRNG noise throughout              |
+-----------------------------------------------------+
|                                                     |
| SECTOR A (Offset 0)                                 |
|  +-----------------------------------------------+  |
|  | Salt(32B)|IV(12B)| AES-256-GCM Ciph||Tag      |  |
|  | CSPRNG   |CSPRNG | Padded payload (zero-fill) |  |
|  +-----------------------------------------------+  |
| Decoy Partition                                     |
| Decrypted by: Primary Passphrase                    |
|                                                     |
| --- SECTOR BOUNDARY (N/2) ---                       |
|                                                     |
| SECTOR B (Offset N/2)                               |
|  +-----------------------------------------------+  |
|  | Salt(32B)|IV(12B)| AES-256-GCM Ciph||Tag      |  |
|  | CSPRNG   |CSPRNG | Padded payload (zero-fill) |  |
|  +-----------------------------------------------+  |
| Hidden Partition                                    |
| Decrypted by: Secondary Passphrase                  |
|                                                     |
+-----------------------------------------------------+
| Remaining bytes: CSPRNG noise (untouched)           |
+-----------------------------------------------------+

Sector boundary: offset = floor(containerSize / 2)
No structural indicator of dual volumes exists.
```

### 4.3 Uniform Random Distribution Properties

Both sectors are embedded within a container that is initially filled entirely with CSPRNG noise. The encrypted partition data overwrites portions of this noise, but because:

1. The salt is random (32 bytes of CSPRNG output)
2. The IV is random (12 bytes of CSPRNG output)
3. The ciphertext is AES-256-GCM output (pseudorandom under the security of AES-256)
4. The remaining bytes retain their original CSPRNG noise

...the resulting byte distribution across the entire container remains statistically uniform. There is no boundary marker, no partition table, no header structure, and no magic bytes that would distinguish encrypted regions from random noise.

**Forensic indistinguishability:** A container holding 1 KB of text in a 10 MB container is byte-for-byte indistinguishable in distribution from a container holding 5 MB of files in a 10 MB container. The adversary cannot determine whether a container holds one volume or two.

### 4.4 Cross-Sector Cryptographic Isolation

- **Independent PBKDF2 invocations:** Each sector uses the same salt but a different passphrase, producing independent base keys.
- **Independent HKDF expansions:** Each base key is expanded with the same tier-info context but via separate HKDF invocations.
- **Cross-sector key isolation:** Knowledge of the primary passphrase reveals nothing about the secondary passphrase or its derived key. The two keys are cryptographically independent.
- **AES-GCM authentication:** Each sector has its own authentication tag. A wrong passphrase on Sector A produces a tag mismatch, which is indistinguishable from data corruption — it does not leak information about Sector B.

## 6. Threat Model & Security Proofs

### 6.1 Ciphertext Tampering & Malleability

**Attack:** Adversary modifies ciphertext bytes, IV, or salt in a stored container.

**Defense:** AES-256-GCM provides 128-bit authentication integrity. Any modification to the ciphertext, IV, or associated data causes the GCM authentication tag verification to fail with probability $1 - 2^{-128}$. The decryption function catches the `OperationError` and returns a generic `"Decryption failed / Data corrupted"` message, leaking no information about the nature or location of the tampering.

**Proof:** The GCM authentication tag $T$ is computed as:
$$T = \text{GHASH}(H, A, C) \oplus E_K(J_0)$$
where $H$ is the hash subkey, $A$ is additional authenticated data, $C$ is the ciphertext, and $J_0$ is the counter block. Any modification to $C$ or $IV$ (which affects $J_0$) produces a different $T$ with overwhelming probability.

**Test verification:** `test-trapdoor.js:4` — Forged signature produces different HKDF key → AES-GCM tag mismatch → zero bytes recovered.

### 6.2 Key Derivation Brute-Force Resistance

**Attack:** Adversary attempts to brute-force the passphrase offline.

**Defense:** PBKDF2-SHA-256 with 100,000 iterations provides $O(100{,}000)$ computational cost per guess. On a modern GPU cluster capable of $10^{10}$ SHA-256 hashes/second, the effective rate is $\approx 10^5$ guesses/second, requiring $\approx 10^{14}$ seconds (≈3.2 million years) for a 12-character random alphanumeric passphrase.

### 6.3 Rubber-Hose Cryptanalysis

**Attack:** Adversary coerces operator to reveal passphrases.

**Defense:** Dual-partition plausible deniability. The operator reveals only the primary passphrase, decrypting the decoy partition. The hidden partition remains cryptographically inaccessible. The container provides no structural evidence that a second partition exists.

**Formal argument:** Let $C$ be a container of size $N$. A single-volume container encrypted with AES-256-GCM produces ciphertext indistinguishable from random. A dual-volume container (two sectors of size $N/2$) also produces ciphertext indistinguishable from random. An adversary observing $C$ cannot distinguish between these cases without the decryption keys. The probability of detecting dual-volume structure is bounded by the distinguishing advantage of AES-256-GCM, which is negligible ($\leq 2^{-128}$).

### 6.4 Cold-Boot & RAM Dump Attacks

**Attack:** Adversary captures RAM contents after power-off or during operation.

**Defense:**

- **5-minute auto-purge:** Decrypted content exists in RAM for at most 300 seconds of inactivity.
- **Manual LOCK & PURGE:** Operator can zero all buffers immediately.
- **Buffer zeroization:** All 26 call sites ensure decrypted content is overwritten with `0x00` before reference release.
- **Minimal exposure window:** Encryption/decryption operations complete in <100ms for typical payloads.

**Limitation:** If the device is seized while actively unlocked and within the 5-minute window, memory forensics may recover decrypted content. Mitigation: use the auto-lock and LOCK & PURGE features; operate on a system with encrypted memory (e.g., Linux with AMD SEV or Intel TDX).

### 6.5 DevTools DOM Patching & Console Manipulation

**Attack:** Adversary with live browser access inspects DOM or JavaScript console for decrypted content.

**Defense:**

- **DOM cleared on purge:** `purgeDecryptedState()` sets `innerHTML = ""` on all extraction containers and hides the decrypted section.
- **Object URLs revoked:** All blob URLs are revoked via `URL.revokeObjectURL()`.
- **Typed arrays zeroed:** All tracked decrypted buffers are zeroed via `.fill(0)`.
- **Form fields cleared:** All password inputs are reset to empty strings.
- **Console state:** All sensitive variables (`_pendingVaultBytes`, `_decryptedState.typedArrays`) are zeroed. Console inspection after purge reveals only zeroed buffers.

### 7.2 Size-Correlation Resistance

Containers are padded to fixed MiB-aligned presets. The padding strategy ensures:

1. Both sectors are padded to identical sizes within the container
2. Payload data is zero-padded to fill the sector's allocated capacity
3. Remaining bytes retain original CSPRNG noise
4. Final container size is rounded to the nearest MiB boundary

**Consequence:** A 10 MB container with 100 bytes of plaintext is byte-for-byte identical in size to a 10 MB container with 5 MB of plaintext.

## 8. Air-Gapped Operation

### 8.1 Offline-First Architecture

ID-CLOSE VAULT is a Progressive Web App (PWA) with a service worker implementing cache-first strategy:

1. **First load:** All core assets precached: `index.html`, `vault.js`, `vault-worker.js`, `vault-ui.js`, `license-verify.js`, images, manifest.
2. **Subsequent loads:** Service worker serves from cache; zero network requests.
3. **Air-gap transfer:**
   - Load application on networked machine
   - Verify service worker is active (DevTools → Application → Service Workers)
   - Disconnect all network adapters (WiFi, Ethernet, Bluetooth, cellular)
   - All subsequent operations execute offline with zero network packets

### 8.2 Recommended Air-Gapped Environments
